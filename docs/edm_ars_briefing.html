System briefing · for comment

An automated research pipeline, and the reviewer that gates it

EDM-ARS turns a dataset and a research question into a submission-ready manuscript. LSAR reviews that manuscript against calibrated venue thresholds derived from real published papers. This is what the two systems do, what they have produced, what they cost to run — and what went wrong last week, which turned out to be the most interesting part.

EDM-ARS v5 / LSAR v0.4 All figures measured from run artifacts unless labelled otherwise

What the system does

Give EDM-ARS a research prompt and a curated dataset. Six LLM agents, coordinated by a deterministic state machine, formulate a research question, build the analytic sample, run the estimation battery, critique their own work, and write a complete LaTeX manuscript with real citations retrieved from Semantic Scholar and arXiv. The manuscript is then compiled and submitted to LSAR, a separate six-stage reviewer that scores it on eight dimensions against thresholds calibrated from published papers at the target venue.

Nothing about the loop is aspirational: it runs end to end unattended, and the artifacts below come from real runs on real NCES data.

Architecture — EDM-ARS

Agents are stateless workers; all control flow lives in the orchestrator, a ten-state machine that checkpoints after every stage and can resume mid-run. The important design decision is that an agent never decides what happens next — the Critic emits a review, but a deterministic evaluator recomputes the verdict from the issue counts and overrides the model when they disagree.

Architecture — LSAR, the reviewer

LSAR is a separate program with no access to the pipeline's internals. It receives only the compiled PDF, exactly as a human reviewer would. That independence is the point — and, as the last section describes, it is also the source of the system's sharpest blind spot.

The gate — what “good enough” means

A score out of ten means nothing on its own. So each venue's threshold is derived empirically: fetch real published papers from that venue, review them with the same reviewer, and set the bar at the 25th percentile of what that venue actually publishes. A manuscript passes if it scores like the weaker quartile of the real thing.

What went wrong, and why it is the headline

An audit of the first paper routed to AERA Open found it had passed its gate at 7.5 while containing fabricated numbers: handed an empty cell-means table by the analysis stage, the Writer invented a plausible one. Investigating the reviewer that had waved it through surfaced something worse.

Root cause — LSAR

The scorer builds its prompt from the review's strengths and weaknesses lists and nothing else. The output template orders strengths before weaknesses, and the token cap was set below what the templates ask for. So when a review was truncated it lost exactly its criticism, and the paper was then graded on its praise alone.

21% of all 57 historical reviews were degenerate, and they scored +0.83 higher than complete ones. One anchor had a zero-byte review and scored 7.4 “Accept”.

What it contaminated

  • 5 of 9 JLA calibration anchors
  • 1 of 13 JEDM anchors, 1 of 12 AERA Open anchors
  • The gating sample of the audited run itself

What it did not do

Recomputing every threshold without the degenerate reviews moves JEDM −0.08, JLA −0.12, AERA Open 0.00. Inflated scores sit above a lower-tail P25 and drop out almost without moving it. The published bars were approximately sound; the damage was per-decision.

The controlled test

After shipping the fixes, the same paper was re-run from the same spec on the same data. The analysis produced the identical estimate and the identical empty inputs. The result is the cleanest evidence in the project:

The finding worth arguing about

Telling the model not to fabricate did not work. The prompt-level fix — rendering every null field as NOT AVAILABLE — do not report a value — changed nothing; the Writer invented the same table anyway. Only the deterministic checker caught it, and precisely: 111 of 125 numerals in the manuscript were verified as real, and the 14 that were not are the ones it flagged.

Every defence that failed was an instruction to a model. Every defence that held was code.

Time and cost

Until this week the honest answer to “what does a paper cost?” was that nobody knew. Runs recorded prompt and completion tokens summed into a single number, which cannot be priced — input and output cost different amounts, and cache hits differ again. The figure circulating in the project documentation (“$5–7 per run”) was an unverified estimate inherited from a retired model provider.

Token metering now records prompt, completion and cached-input counts separately per call. The figures below come from one fully instrumented run: 21 pipeline calls plus 63 calls across six sampled LSAR reviews. Counts are measured; dollars are those counts at the configured DeepSeek rate, stated in config.yaml so it can be checked.

The single largest lever is not the model tier — it is the prompt cache. 74% of all input tokens were cache hits, billed at roughly a tenth of a miss. A summed token count, which is all the system recorded until this week, cannot see that at all.

Why this number is worth stating carefully

The budget check in this codebase priced runs at a hardcoded $15 per million tokens — a rate left behind when the stack moved providers. On this run it would have reported $10.92 against a measured $0.15: a 120× overstatement, in the direction that makes a system look more expensive to operate than it is. The published “$5–7 per run” figure came from the same era and was never measured.

Where this goes next

Immediate

  • Stop the fabrication at source. Detection works; the Writer still invents values when handed nulls, and the analysis stage still emits them.
  • Two more venues need re-anchoring. JEDM and JLA are calibrated against a review template written for a different venue.
  • Citation uptake. The pipeline assembles 66 usable references and the Writer cites 24.

Longer arc

  • Research taste. Automated idea ranking has been built and measured twice — it correlates with nothing. It stays advisory, refusing live selection in code, until it demonstrably works.
  • Self-improvement. A retrospective agent proposing its own PR-gated diffs against a benchmark battery.
  • Human evaluation. Blind review of system output against matched human-written papers — the only measurement that settles the question.
What I would most like your view on
  • Is a P25-of-published-papers bar the right definition of “good enough”, or does it encode a venue's weakest quartile as the target?
  • An LLM reviewer scoring LLM-written papers is circular. What independent check would you find convincing?
  • Where is the line between an honest research instrument and an automated paper mill — and what should this system refuse to do?
  • If you had one run to spend, what question would you point it at?
